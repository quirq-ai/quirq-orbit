The sandbox an AI coding agent works in. One executor runs for one chat: it is a container that connects out to an OpenAI Agents API session (a self_hosted environment) and runs the shell commands the agent asks for, in a workspace folder, as an unprivileged user.

It is small on purpose: one supervisor process (executor.mjs, about 100 lines, no dependencies) around one codex exec-server.

How it fits

Agents Hub ──creates──▶ Launchpad app (this image) ──dials out──▶ OpenAI Agents API session
   (one per chat)          codex exec-server                         (the agent's turns)
  1. A user starts a chat in their Agents Hub. The hub opens an OpenAI Agents session and gets an environment id and an environment address for it.
  2. The hub asks Launchpad (a platform that runs apps on Kubernetes) to create an app from the agents-executor template, passing those values.
  3. Launchpad starts this image with the values as env. The supervisor starts codex exec-server, which connects to the session. From then on the agent's shell commands run here.
  4. When the chat is torn down, the hub deletes the app.

Files

File What
executor.mjs The supervisor: starts codex exec-server, restarts it if it dies, answers the health probe, stops it cleanly on SIGTERM
config.mjs Reads and checks the env values before they are used
test/config.test.mjs Tests for config.mjs
Dockerfile The image: Node 22, git, ripgrep, jq, Python 3, make, g++, and a pinned @openai/codex
launchpad-template/agents-executor/template.yaml The Launchpad template: the parameters the hub passes and the env they become

Contract

Launchpad sets these env values on each executor app (from the template):

Variable What Checked by config.mjs
ENVIRONMENT_ID The OpenAI session's environment id Letters, digits, _, -; 1 to 128 characters
REMOTE_URL The OpenAI session's environment address Must be https:// or wss://
CODEX_API_KEY The user's OpenAI environment key (a secret parameter) Must be present
WORKSPACE_DIR Where the agent works. Default /workspace/work One folder directly under /workspace/
PORT The health port. Default 8080

If a value is missing or malformed, the executor prints which one and exits with code 1.

Health: GET /healthz on the port answers 200 with {"state": "starting|running|restarting|stopping", "restarts": n}.

For local runs only: CODEX_BIN (default codex), RUN_AS_UID and RUN_AS_GID (default 1000).

Behaviour

  • Outbound only. The executor dials out to OpenAI. Nothing calls into it except the health probe.
  • The agent is not root. The supervisor starts as root only so it can give the workspace to uid 1000 (the image's node user) and start codex exec-server as that user. Every command the agent runs is that user's.
  • A minimal environment. codex exec-server gets PATH, HOME, LANG, CODEX_HOME and CODEX_API_KEY, and nothing else from the container's env. It needs the key to connect; that key can only connect environments.
  • Restarts with backoff. If codex exec-server exits, it is started again after 3 s, then 6 s, 12 s, 24 s, then every 30 s. The count shows in /healthz.
  • Clean stop. On SIGTERM or SIGINT it sends SIGTERM to codex exec-server, then SIGKILL after 5 s.
  • No keys in the image. Every key arrives through env when the app starts.
  • The agent can only use what is installed. Add the toolchains your repositories need to the Dockerfile.

Build, test, run

npm test        # Node 22 or later; no keys needed
docker buildx build --platform linux/amd64 --provenance=false -t <registry>/<project>/agents-executor:<version> --push .

To run it by hand you need a real OpenAI Agents session (its environment id and address) and an environment key:

docker run --rm -p 8080:8080 \
  -e ENVIRONMENT_ID=<id> -e REMOTE_URL=<address> -e CODEX_API_KEY=<environment key> \
  <registry>/<project>/agents-executor:<version>
curl http://localhost:8080/healthz

The codex version is pinned in the Dockerfile (CODEX_VERSION) because exec-server ships in the CLI's alpha channel: a rebuild should never change behaviour by itself.

The template

launchpad-template/agents-executor/template.yaml is in Launchpad's own template format, so it is only usable on a Launchpad installation. It is here because it is the other half of the contract: it shows the three parameters the hub passes (environmentId, remoteUrl, environmentKey), the env they become, the size, the 10 GB /workspace volume, and fsGroup: 1000 (so uid 1000 can write to the volume). Replace <project> in image: with the registry project the image is pushed to.
