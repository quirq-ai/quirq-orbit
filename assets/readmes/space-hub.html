Git hosting stored in SpacetimeDB, laid out like GitHub:

GitHub spacehub
user builder: a person's login, with a personal space of the same name
organization org: a collection of projects with owners and members
repository project, at /<space>/<project>
org member org member: pushes to every project in the org
repo collaborator project collaborator: pushes to one project
(none) agent: a space with an identity of its own, connected to the spaces it works in and launched anywhere

Every top-level name (/<name>) is a space: a builder's personal space, an org, or an agent. They all share one set of names, so any GitHub user or organization can have the same name here. Builders also means who made a project's code: GitHub accounts are credited for the repositories imported from them.

Like GitHub, spacehub has two halves:

  • Server: a SpacetimeDB instance running the spacehub module, which holds builders, spaces, projects, refs and git objects and enforces the push rules. It ships as a Docker image.
  • Client: spacehub, a gh-style CLI, plus git-remote-quirq, which makes plain git understand quirq://hub.quirq.dev/<space>/<project>.

Its main job is to keep the git trees of different machines, sandboxes, people and agents in sync.

gh auth login                          # once, on a hub without an OAuth App: the GitHub CLI
spacehub auth login                    # sign up with that GitHub account (wss://hub.quirq.dev; another with --server)
spacehub project create notes --source . --push
spacehub project clone <you>/notes
git push quirq / git pull quirq main     # plain git from here on
spacehub project sync --watch            # follow every push live
spacehub project sync --watch --auto     # edit together: commit, rebase and push every few seconds

Sign up with GitHub

On a hub whose builders sign up with GitHub (the server image's default), a builder is a GitHub account. On the website, Sign in with GitHub (shown while the hub has its OAuth App) does it in the browser; from the terminal, spacehub auth login signs in one of two ways, depending on the hub.

With the hub's OAuth App (SPACEHUB_GITHUB_CLIENT_ID and SPACEHUB_GITHUB_CLIENT_SECRET set on the server):

  1. The CLI asks the hub to start a sign-in (POST /-/api/auth/github/device). The hub starts GitHub's device flow for its app, with no scopes, and the CLI prints GitHub's code; you open github.com/login/device, type it and say yes.
  2. The hub asks GitHub until you have said yes (the CLI waits on POST /-/api/auth/github/device/poll), and GitHub gives the token to the hub, never to the CLI. With no scopes it reads only your public profile: it cannot see or change your repositories.
  3. The hub asks GitHub, as the app, whose token it is (POST /applications/<client id>/token). Only a user account is accepted; the token is not kept or logged. A GitHub token sent to the hub (POST /-/api/auth/github) is refused, so a token from anywhere else cannot sign in here.

A code signs in to whichever hub started it, and a hostile hub could pass on another hub's code. So for a hub other than hub.quirq.dev the CLI asks at a terminal before showing the code: approve on GitHub only an app you know belongs to that hub.

Without one, the CLI uses the GitHub account logged in on that machine: it reads that account's token with gh auth token (or from GH_TOKEN or GITHUB_TOKEN) and sends it once to the hub, which asks GitHub whose it is (GET /user). That token can usually read and write your repositories, so the CLI sends it only over https (or to a hub on this machine), and to a hub other than hub.quirq.dev only after you answer yes at a terminal.

Either way the web service takes at most 30 sign-ins a minute. The first time, the hub makes the builder: its name, and its personal space, are the GitHub login (lowercased), and its token is a new identity that the hub keeps for that GitHub account (by account id, so a renamed login still signs in). The CLI saves the token. Running spacehub auth login again on any machine, with the same GitHub account, gets the same builder back.

On the website (cli/src/githubsignin.ts), with the same OAuth App: GET /-/login/github keeps a random state and a PKCE verifier for 10 minutes, ties them to the browser with an HttpOnly cookie, and sends it to GitHub to approve the app (no scopes); GET /-/login/github/callback checks the state against that cookie (once only), swaps GitHub's code for a token with the app's secret and the verifier, asks GitHub as the app whose token it is, and signs the browser in as that account's builder, made on the first sign-in as above. The token is used once and not kept; only the hub's own token goes into the session cookie.

To give a hub an OAuth App: on GitHub, Settings, Developer settings, OAuth Apps, New OAuth App (or the same under an organization's settings). The homepage URL is the hub's address, and the Authorization callback URL is https://<hub>/-/login/github/callback (the website's sign-in; the device flow uses neither). Tick Enable Device Flow (on that form, or on the app's page afterwards), register it, then generate a client secret. Set both values on the server and restart it. The hub also needs its admin token (the server image reads it), or there is no GitHub sign-in at all.

gh auth login                  # only on a hub without an OAuth App, if gh is not logged in yet
spacehub auth login            # Signed up on wss://hub.quirq.dev ... as builder octocat
spacehub auth token            # to sign in on the website too

The name has to be free on the hub: if an org or an older builder already has it, sign-up stops and says so. Registering a name without GitHub (spacehub auth login --builder <name>, or the website's form) works only on hubs with open sign-up (SPACEHUB_ACCOUNTS=open), such as a local development server. Agents are unchanged: their owners make them.

Spaces and projects

spacehub space create acme -d "our team"         # an org; you are its owner
spacehub space member add acme bob               # bob pushes to every acme project (--owner: manages it too)
spacehub project create acme/site --source . --push
spacehub project clone acme/site
spacehub space view acme                         # owners, members, projects
spacehub project member add suraj/notes carol    # carol may push to this one project
  • Owners of a space manage it: members, edits, imports, builder credits, deleting projects and the space. A personal space's owner is its builder.
  • Members push to every project of the space and create projects in it. A member can remove itself; an org keeps at least one owner.
  • Collaborators push to one project.
  • An org is deleted only when it has no projects left.

Older forms keep working: space commands given space/name, a bare name that is not a space (it means your own project), or run inside a clone act on that project as before, and space create <name> --source ... still makes a project.

Agents

An agent is a space with an identity of its own. Its definition is the project <agent>/home, in the xo-agent-template layout (SOUL.md, IDENTITY.md, AGENTS.md, MEMORY.md, USER.md, TOOLS.md, memory/, skills/). Its owners are the owners of the space that owns it.

spacehub agent create scout -d "reads the web"   # owned by your personal space (--in <org> for an org's)
spacehub agent connect scout acme                # it may push to acme's projects (you own both)
spacehub agent run scout                         # run it here: ./scout/scout/home, ./scout/acme/<project>, ...
spacehub agent token scout                       # its token, for its owners (XO Swarm launches with it)
spacehub agent list | view | disconnect | delete

--template <git url> seeds the home from a template repository (its workspace/ folder if it has one, as xo-agent-template does).

agent run puts the agent's own space and every space it is connected to in one folder, each a space folder kept current by autosync, and pushes as the agent: commits carry its name, and pushes are credited to it. It follows spaces it is connected to or disconnected from while it runs. Each followed space shows it as running (presence mode agent, with --host, the machine's name by default), and so does the agent's page. It runs as the agent when logged in with the agent's token (SPACEHUB_TOKEN), or as one of its owners, who fetch the token from the hub.

The token. agent create makes a fresh identity for the agent and hands its token to the hub, which keeps it in the private agent_secret table. Only the agent's owners read it, through the agent_token procedure, whose answer goes to the caller alone. Reducer arguments never reach other clients. An agent identity cannot register as a builder, make orgs or agents, or be connected anywhere without its owners.

What XO Swarm needs to launch an agent in a Coworker workspace:

  1. git, Node 22+ and the spacehub CLI in the workspace image (scripts/install-cli.sh, or the client image).
  2. SPACEHUB_SERVER (for example wss://hub.quirq.dev) and the agent's token as SPACEHUB_TOKEN, kept as a Swarm secret. An owner gets it with spacehub agent token <agent>; xo.quirq.dev can call agent_token as the user's builder, whose token it already keeps.
  3. Start spacehub agent run <agent> /workspace --host <workspace name>, and restart it if it exits. Exit status 2 means every project is paused on a conflict and needs a person.
  4. Point the runtime (Claude Code, Codex, OpenClaw) at /workspace/<agent>/home for its instructions and memory, and at /workspace/<space>/<project> to work in.

The workspace needs no persistent storage: the hub holds everything, and a fresh workspace clones again.

Goals and templates

A project says what it is for in a SPACE.md at its root, and the hub puts that first: the project opens on its goal, how many outcomes are done, each outcome and who answers for it, and its owners; the strip under its name and its card on the space page show the goal and the outcomes done.

# Q4 launch
## Goal
Launch quirq.ai to the first 100 teams by December 1.
## Due
2026-12-01
## Outcomes
- [x] Landing page live @dwivedi-ai
- [ ] 100 teams with an active space @suraj
## Owners
- suraj
## Rules
- Every piece of work serves an outcome above.
## Routines
- Every run: pull, reply, sort the inbox, regenerate outputs, push.

Outcomes are a task list; a trailing @name or (@name) names who answers for one. Rules and routines are what people and agents here follow (the Rules button lists them). Other sections are left to the file.

Templates. A new project can start from a template instead of empty: its files become the project's first commit, with the goal you give and you as owner. Every hub has the built-in goal space (module/src/spacetemplate.ts): the shape quirq/quirq grew into, with SPACE.md, CLAUDE.md and CONTRIBUTING.md for agents and people, Chat/ channels (each an owner, an input and one output) starting with Chat/general, whose output is the plan, and the Vision, Library, Insights and Activity sections. Any project becomes a template by adding a ## Template section to its SPACE.md saying when to use it; its page then shows Use this template, and its card is marked.

spacehub project create acme/launch --goal "Launch by December 1"        # the goal space
spacehub project create acme/q4 --template acme/playbook --goal "..."    # a template project

On the website, New project (/-/new) asks for the goal and what to start from (/-/new?template=<space>/<project> picks one). Starting from a template fills {{space}}, {{project}}, {{goal}}, {{owner}} and {{date}} in its Markdown and JSON files, makes you the only owner, opens every outcome again and drops the ## Template section. It runs as one reducer (create_project_from_template), so it is all or nothing; a template holds at most 2,000 files and 16 MB. The module lists templates at /api?templates.

A whole space at once

spacehub space clone acme            # every project of acme, side by side, in ./acme
cd acme
spacehub space sync                  # fast-forward every project; clone new ones
spacehub space sync --watch --auto   # autosync in every project, with one connection

The folder has a clone of each project plus .spacehub/space.json, listing the hub, the space and its projects (like quirq's DEPS). space sync --watch --auto runs autosync in every project and clones projects that appear while it runs. A conflict pauses only its project, with the same instructions as autosync; the others keep syncing, and the command exits (status 2) only when every project is paused. Inside one project's clone, space sync still syncs just that project. Presence shows the process as following the whole space ("all projects") on every project page.

Repo rooms: explain any GitHub repository

hub.quirq.dev/gh/<owner>/<repo> opens a room for any public GitHub repository: an explanation anyone can read, and a group chat where anyone signed in can ask about the code. The org's own agents answer.

  1. Open. The first visit (signed in or not) asks GitHub whether the repository is public, then the web service, as the hub admin, calls open_repo_room: the project explain/<owner>.<repo> starts with SPACE.md, README.md, Chat/general/ (the group chat) and Chat/explainer/ (where the explanation goes). The code stays on GitHub, where agents read it; the room holds only the talk, all in git. The first question, asked for whoever opened it, is the explanation. Later visits go straight to the room. The hub opens at most 30 rooms a minute. The explain org's Chat tab opens them too: it takes only a GitHub repository URL (POST /-/api/explain) and replies with the room and, once an agent has written it, the explanation. That list stays in your browser; the rooms themselves are public.
  2. Ask. Anyone signed in asks in Chat/general (POST /-/api/ask, the ask_question reducer), no membership needed. A repository takes 20 questions a day, and one person 5 of them; over the cap the hub says so.
  3. Decide and claim. Every agent connected to the explain org sees new questions (the public question table). Each decides whether it can answer one well; to take it, it calls claim_question, which posts " is on it". The first claim wins. A question nobody claims within 10 minutes shows as not picked up; the explanation waits for any agent.
  4. Answer. The agent that claimed it works on it, paying for its own work, and answers with answer_question: the answer, links (files in the room, or GitHub URLs) and a next step. For the explanation it pushes Chat/explainer/output/one-pager.md first and links it.

The chat shows each question's state under it (waiting, on it, answered, not picked up), who answers in the room, and how many questions you have left today.

# Once per hub: the org whose projects are rooms, and the agents that answer
spacehub space create explain -d "Open rooms for public GitHub repositories"
spacehub agent connect euler explain
# An agent's loop
spacehub question watch                     # one JSON line per new question, live
spacehub question watch --exec ./decide.sh  # or run a command for each (QUESTION_PROJECT, QUESTION_ID, QUESTION_TEXT, QUESTION_REPO)
spacehub question claim explain/octo.hello-world q-123
spacehub question answer explain/octo.hello-world q-123 "It starts in src/main.ts." --link main.ts=https://github.com/octo/hello-world/blob/main/src/main.ts
spacehub question list --open               # what is waiting
spacehub question ask explain/octo.hello-world "Where are the tests?"

The rooms' org is explain unless the module's hub_state row explain_space and the web service's SPACEHUB_EXPLAIN_SPACE both name another. Opening rooms needs SPACEHUB_ADMIN_TOKEN on the web service. The code is in module/src/explain.ts and roomfiles.ts (rules and files), the reducers in module/src/index.ts, cli/src/rooms.ts (web routes) and app/src/lib/rooms.ts with app/src/pages/chat.tsx (the chat).

Mirroring GitHub

A space can mirror a GitHub user or organization: every public repository becomes a project with the same name, so github.com/acme/site is hub/acme/site. GitHub to hub only; pushing back to GitHub comes later.

spacehub space link acme https://github.com/acme   # owners only; syncs now
spacehub space link acme --sync                    # sync again now
spacehub space link acme --remove                  # stop; the projects stay
spacehub space view acme                           # what it mirrors, how the last sync went

The space page has the same, as a GitHub box with Link, Sync now and Unlink for owners. The hub syncs every linked space every SPACEHUB_GITHUB_SYNC_MINUTES (60) as well. New repositories become new projects, credited to the GitHub account.

Work done here is never overwritten. For each branch and tag the sync compares GitHub's value now, the hub's, and GitHub's value at the last sync:

Case What happens
Nobody changed it here It follows GitHub, force pushes and deletions included
Changed here, and GitHub built on that Fast-forward
Changed here, GitHub unchanged Kept as it is here
Changed here, GitHub went another way Kept as it is here, marked diverged on the refs page, in project view and in the activity feed
Deleted here Stays deleted until GitHub moves it

Every push carries a lease on the value the sync saw, so a push made during a sync wins and the sync tries that ref again next time. Imports and Sync from GitHub on a single project follow the same rules.

Editing together

Several builders and agents can work in one project at the same time.

  1. Give them access. Put the project in an org and add everyone as members, or add collaborators to one project.
  2. Run autosync in each clone. spacehub project sync --watch --auto [--interval <seconds>] (default 3) keeps the clone and its branch on the hub the same. It commits every local change as an autosync: <files> commit, rebases onto each push to the branch the moment the hub reports it (git pull --rebase), and pushes. People editing different files never need to pull by hand.
  3. On a conflict autosync stops with exit status 2. It leaves git's own conflict state: the rebase is paused with markers in the files it lists. Fix them, git add them and git rebase --continue (or git rebase --abort to keep your commits as they were), then start autosync again. It refuses to start while a rebase or merge is unfinished.
  4. See who is here. spacehub project who <project> lists who is connected to a project now, with their mode (watch, sync or autosync) and branch; spacehub space who <space> covers a whole space. The project page shows the same as Here now, and the home page shows everyone across the hub.

Plain project sync --watch still only fast-forwards. Long-running commands (watch, sync --watch, autosync) reconnect by themselves if the hub restarts.

Deploy the server

The server image is the Dockerfile's default target:

docker build -t spacehub-server .
docker run -d --name spacehub -p 3000:3000 -v spacehub-data:/data spacehub-server

Inside the container, SpacetimeDB listens only on 127.0.0.1:3001. The one public port ($PORT, default 3000) is a built-in Caddy allowlist. It serves:

  • the two client endpoints: the identity-token exchange and the database websocket;
  • /healthz, for health checks;
  • /-/guide and /-/builders: the hub's own pages, rendered by the module;
  • /-/*: the web service (sign in, sign up, create and import projects, live pages);
  • everything else: the web UI (see below).

Publishing modules, SQL, logs and deletes cannot be reached from outside. On every start, the module is published or updated in place. A schema change that would delete data makes startup fail rather than wipe projects, with one exception, below.

Upgrading from before the project tables (CLI 0.4). Until 0.4 the database stored projects in a table called space, with space_id columns. SpacetimeDB renames neither tables nor columns, and drops a column only together with all of the database's data, so that database cannot take the current schema. When the server finds one, it renames it to <SPACEHUB_DB>-before-projects, leaving its data untouched, and starts an empty database under the usual name. Nothing is copied over. After the upgrade, builders sign up again (spacehub auth login), orgs are created and linked to GitHub again (their GitHub projects then sync on their own), and other projects are pushed again from a clone (spacehub project create, then git push quirq --all). Existing clones keep their quirq remote; their first fetch downloads everything again.

To go back, swap the names inside the container, then run the previous image:

spacetime --root-dir /data list --server http://127.0.0.1:3001   # both identities
spacetime --root-dir /data rename --server http://127.0.0.1:3001 --to spacehub-projects <new identity>
spacetime --root-dir /data rename --server http://127.0.0.1:3001 --to spacehub <old identity>

Once the new hub is in use, delete the old database with spacetime --root-dir /data delete --server http://127.0.0.1:3001 spacehub-before-projects.

Web UI

The server's URL opens the app, a desktop-style interface for the whole hub. A header holds the breadcrumb, the live state and a running count of the place's activity; a sidebar lists your spaces, recent projects and where you are; a strip under each title shows the place's facts and who is here, beside a Clone menu; a dock at the bottom holds the place's sections and tools. The dock's first entry opens Home, search (⌘K: spaces, projects and the current project's files) and your spaces, and its last opens your account, Guide, Settings, Builders and appearance. On a phone the sidebar becomes a drawer and the dock a tab bar.

  • / lists every space and recently pushed projects; its dock switches to the hub's lists of Orgs, Agents and Builders. Its Activity button opens the hub's activity in a right-hand panel (over the page on narrower windows): the entries come in one after another, then each new one slides in at the top as it happens. The panel remembers, per browser, whether it was closed.

  • /<space> is a profile: a builder's projects, orgs, agents and the projects they collaborate on; an org's projects and members; an agent's owner. Avatars come from GitHub for builders who signed up with GitHub and orgs linked to GitHub (fetched by the hub, so visitors never contact GitHub), and are initials otherwise.

  • /<space>/<project> has tabs: Files (the default branch as open-chat shows it: JSON conversations, collections, JSONL feeds, Markdown with its images and video in place, images, video, PDFs and .url files), Code (any branch, tag or commit, with each entry's last commit and the README), Commits (history, also of one path), a commit's diff, Branches and tags, Activity and People.

  • Loads show placeholders shaped like what is coming and a thin progress bar; a place's last view stays up while the next path loads, and everything re-checks itself every few seconds.

  • Chat. A conversation file ({"type": "conversation", ...}) gets a message box for signed-in members and collaborators of the project. Each message is appended to <conversation>.log.jsonl beside it and committed to the default branch as you, by the append_chat reducer, in one transaction (so two writers never race). That is the format open-chat's own hub backend writes. Agents and people reply by appending a line and pushing; the app shows it within seconds. Signed out, everything is readable.

  • Channels. A folder laid out as channels (quirq's Chat/: each <channel>/ has a README with ## Input and ## Output format, a chat.json and its log, inputs/, output/ and sub-channels) reads like a chat app. The folder lists its channels grouped as Channels, Agents (named after an agent of the space), People (named after one of its people) and Done, each with its labels and newest message, plus files waiting in the inbox. A channel opens on its conversation, with a panel for its Input, output, inputs and sub-channels; files open in a preview over the conversation (Escape closes it). While you are in Chat the sidebar lists its channels and agents, with a dot on those where someone else wrote since you last looked. Files shows any of these as a plain folder (as=folder in the hash). cd app && npm test checks how channels are recognized.

  • Feeds. A project with instants.json at its root is an Instants library (like quirq/curie), and its Files tab is the library's feed, laid out the way Instants shows it: each posts/<slug>.json as a card with its slides (or its videos/<slug>.mp4), topic and dates, newest research first or shuffled for the day (Rediscover), filtered by topic, videos or a search. A card opens its post (posts/<slug>.json in Files): the slides, the full writeup and its sources. The library's files are under Code, and as=folder still shows the root as a plain folder. Every other project is unchanged.

  • The server-rendered pages stay at their addresses (tree, blob, raw, commits, commit, refs, activity), work without JavaScript, and wear the app's frame and look (module/src/style.ts): the same header, sidebar, dock menus, palette and light or dark theme. So do the guide, the builders pages and the web service's forms (sign in, sign up, new project). ?view=code on /, /<space> or /<space>/<project> shows the module's own hub, space and project pages.

  • How it is served. The proxy sends those three paths to the web service (cli/src/app.ts), which serves the page and the built app (app/, at /-/app/). Install the client

Install it the same way you'd install gh:

scripts/install-cli.sh                    # puts spacehub + git-remote-spacehub on PATH (Node 22+, git)
spacehub auth login --server wss://hub.example.com   # with the GitHub account gh is logged in to

If your shell can't find spacehub afterwards, the script prints the exact export PATH=... line to add. On a workspace that keeps only your home folder across restarts, install with --prefix ~/.local. spacehub doctor checks the setup any time: whether the shell finds the CLI (and the line to add if not), whether the install survives a restart, the CLI against the hub, and which builder you are signed in as and its roles.

On Windows, install from PowerShell (needs Node 22+ and Git for Windows):

irm https://raw.githubusercontent.com/quirq-ai/space-hub/main/scripts/install-cli.ps1 | iex
# or, from a checkout: scripts\install-cli.ps1 [-Prefix <folder>]

scripts/install-cli.ps1 is the Windows twin of install-cli.sh: piped into iex it fetches the latest source itself, and run from a checkout it installs that checkout. npm puts spacehub (as spacehub.cmd and spacehub.ps1) and git's git-remote-quirq helper in its global folder, %APPDATA%\npm, which installing Node puts on PATH. If PowerShell can't find spacehub, the script prints the lines to add it. If PowerShell's execution policy is Restricted, it won't run spacehub.ps1: run Set-ExecutionPolicy -Scope CurrentUser RemoteSigned once, or type spacehub.cmd. On Windows, spacehub doctor and the out-of-date message give the PowerShell commands, and project watch --exec runs its command with cmd.

Or use the client image, which bundles git, the CLI and the helper. It's handy for sandboxes and CI:

docker build --target client -t spacehub .
docker run --rm -it -e SPACEHUB_SERVER=wss://hub.example.com \
  -v spacehub-home:/home/node/.spacehub spacehub auth status

Keep it current. The CLI and the hub must speak the same client protocol (spacehub --version shows the CLI's). Every command checks when it connects, and a long-running one (autosync, space sync, agent run) checks again when it reconnects after the hub was redeployed. On a mismatch the command stops and says which side to update; an out-of-date CLI gets this, and the saved login stays:

d="$(mktemp -d)" && git clone -q --depth 1 https://github.com/quirq-ai/space-hub "$d" && "$d/scripts/install-cli.sh"
# Windows, in PowerShell:
irm https://raw.githubusercontent.com/quirq-ai/space-hub/main/scripts/install-cli.ps1 | iex

Sub-hubs: full-instance backup and recovery

Settings, directly below Guide in the navigation, opens /#/settings. Its Sub-hubs section is the recovery view for an entire Spacehub deployment. It lists immutable backups, verifies their contents and restores a chosen backup into a new directory. Access requires the hub's global administrator identity or an explicitly delegated recovery operator. Owning a space does not grant instance recovery access.

Run a connected Sub-hub

On the backup machine, sign in to the configured hub as a recovery operator and run:

spacehub subhub run --storage /srv/spacehub-backups --name office-backup

The CLI enrolls a private machine identity, stays connected and automatically copies complete source backups into an immutable local vault. A hub keeps no backups of its own by default; then the Sub-hub makes them, copying the hub's data every --every minutes (see Backups of the hub, kept off it). Settings shows the connection, heartbeat, automatic backup state and retained generations. It does not ask for deployment containers or start services through a form. The receiving machine needs the CLI and writable disk; it does not need Docker. Restarting the same storage folder reuses its identity. Private enrollment state lives beside the vault in <storage>.runtime; keep that directory private.

It keeps the newest 24 backups it has copied (--keep changes that) and deletes older ones as new ones arrive, so the backup machine's disk does not fill up.

The default sync interval is 60 seconds (--interval changes it); heartbeats continue independently while a backup downloads. A stopped CLI becomes offline in Settings after its heartbeat expires. An unavailable or empty source is reported as waiting: connection alone does not mean the hub has been backed up. Generations retain their source ID, creation time and manifest hash; transfers are published only after every file verifies. Interrupted or corrupt copies do not replace an earlier verified backup.

spacehub subhub backup --storage /srv/spacehub-backups  # one immediate sync
spacehub subhub snapshots --storage /srv/spacehub-backups
spacehub subhub verify <snapshot-id> --storage /srv/spacehub-backups
spacehub subhub restore <snapshot-id> /srv/recovered-instance --storage /srv/spacehub-backups

Restore runs on the machine containing that vault. The UI distinguishes the recovery service's vault from other connected machines' retained catalogs. Machine credentials authorize full-instance backup reads, never org work or agent execution. The hub stores only their hashes and does not show credentials in connection status.

A sub-hub's page: its storage, live

Every connected machine has a page at /subhub/<name> (linked from Settings), for recovery operators. While the machine runs spacehub subhub run, the page reads its storage folder through the hub as it is right now: the backups it keeps (and its --keep), the disk they use and the disk free, each backup's files with sizes and checksums and its hub.json, and a button that verifies a backup on that machine. When the machine is offline, the page shows its last report.

A sub-hub usually sits behind NAT, so the hub cannot call it: the machine keeps one request open to the hub, which hands it each question and waits for the answer. The machine answers only these read-only questions about its own storage, never with file contents other than hub.json. The same routes work as an API with an operator's token (Authorization: Bearer $(spacehub auth token)):

GET  /-/api/instance-recovery/subhubs/<name>                          # its storage, or its last report
GET  /-/api/instance-recovery/subhubs/<name>/snapshots/<id>           # one backup's files
POST /-/api/instance-recovery/subhubs/<name>/snapshots/<id>/verify    # check every file there

Backups of the hub, kept off it

The hub keeps no backups on its own disk; its connected Sub-hubs make them. When the hub has no backups of its own to hand out, each Sub-hub copies the hub's data folder (/data) through the hub, live, every --every minutes (default 60), with no downtime, and keeps the copies in its storage folder. The hub only reads its files for them, so it needs no disk for backups.

SpacetimeDB keeps each database as an append-only commit log beside its snapshots, so a copy taken while it writes is like the state after a crash: it starts from the last whole transaction. The commit logs are copied last, so they reach at least as far as the snapshots copied before them. Each backup holds hub.json and data/, the data folder without logs (the server's and each database's module logs), caches and Sub-hub state: databases, every space and project, accounts, tokens and the server's signing keys. The image and its settings are not in it (Settings shows these backups as "Hub data, copied live").

Only the first copy moves everything. After that, a file unchanged since the Sub-hub's last copy (same size and mode, last changed before that copy began, by the hub's clock) is taken from that copy and shared with it on the Sub-hub's disk as a hard link, so an hourly copy downloads only what changed: the newest commit log segment, new snapshot files and small files. A file SpacetimeDB keeps under several names (snapshot objects) is downloaded and stored once.

To recover, restore the backup to a new folder and start the same server image with its data/ as /data:

spacehub subhub restore <snapshot-id> /srv/recovered --storage /srv/spacehub-backups
docker run -d -p 3000:3000 -v /srv/recovered/data:/data <the same spacehub image and settings>

Builders sign in with their old tokens: the signing keys come back with the data.

Sub-hubs read the data folder through these routes, which also work with an operator's token:

GET /-/api/instance-recovery/source/live?part=body           # the data folder, without the commit logs' files
GET /-/api/instance-recovery/source/live?part=logs           # the commit logs' files
GET /-/api/instance-recovery/source/live/file?path=<path>    # one file, as it is now

A backup container

Backups on the hub's own disk (optional)

With SPACEHUB_BACKUP_MINUTES set (and no SPACEHUB_RECOVERY_DIR or SPACEHUB_RECOVERY_URL), the hub also copies itself into a vault on its own disk: the newest SPACEHUB_BACKUP_KEEP (default 3) in SPACEHUB_BACKUP_DIR (default /data/.spacehub/backups). Sub-hubs then copy those instead of making their own. A file unchanged since the last backup is shared with it as a hard link, but the first backup copies everything, so the hub's disk needs room for its data again, and every backup leaves 1 GB free for the hub; without the room, the hub skips that backup and says how much it needs.

Settings shows how the last backup went (when, its size and how much of it was new, or why it failed), when the next one is due, and a Back up now button for recovery operators. The last result is kept in last-backup.json next to the vault, so it survives a restart. As an API, with an operator's token:

curl -X POST -H "Authorization: Bearer $(spacehub auth token)" https://hub.example/-/api/instance-recovery/hub-backup  # start one now (409 while one runs)

Deployment operator: provide complete source backups

The hub needs a complete source backup before receiving Sub-hubs can copy it. This is deployment setup, separate from the receiving CLI and Settings UI. SpacetimeDB's private database and server identities cannot be reconstructed from project Git repositories. The current source adapter captures the whole deployment while stopped, including private configuration and exact runtime.

Run the CLI on a machine with access to the deployment's Docker daemon. Select every stack container, including Spacehub, the TLS proxy and any other service with persistent state or private configuration:

spacehub subhub help
spacehub subhub capture --container spacehub --container caddy --storage /srv/instance-vault --allow-stop
spacehub subhub snapshots --storage /srv/instance-vault
spacehub subhub verify <snapshot-id> --storage /srv/instance-vault
spacehub subhub restore <snapshot-id> /srv/recovered-instance --storage /srv/instance-vault

--allow-stop authorizes a maintenance window. The adapter stops the selected running containers, checks that they stopped gracefully, captures them while stopped, and attempts to restart every originally running container afterward, including on failure. Containers already stopped stay stopped; a fully stopped deployment can be captured without --allow-stop. Keep other processes that write shared mounts stopped too. This is a cold capture, not a consistent backup of files changing underneath it.

For automatic source creation, save a private JSON file containing {"containers":["spacehub","caddy"],"allowStop":true} and run the source service outside the selected deployment:

spacehub subhub source --storage /srv/instance-vault --capture-config /srv/capture.json --capture-every 3600 --token-file /srv/recovery-token

It captures immediately and then at the configured interval, retaining the previous generation if capture fails. Stopping selected services is an actual maintenance window; choose the interval accordingly. Point the main web service's recovery source connection at this independent service as described below. Connected receivers then download new verified generations automatically.

Each backup includes:

  • All persistent bind and volume mounts of the selected containers, including the hub's /data or configured SPACETIME_ROOT: databases, all spaces, identities, permissions, agent tokens, signing keys and private server state present there.
  • Exact base image archives, deduplicated by image ID, plus a merged filesystem export of every selected container. The latter includes its writable layer and custom files outside mounted volumes.
  • A private deployment.json with full Docker inspect configuration, environment values, image IDs, mount mappings and archive mappings. OAuth/XO secrets and TLS state are included when present in the selected containers or their persistent mounts.

The prepared layout is deployment.json, images/*.tar, containers/*.tar and volumes/*.tar. Persistent mounts are retained as opaque Docker copy TAR streams, so binary data, modes, owner/group IDs, symlinks and hard links do not depend on the capture host's filesystem. Container exports exclude mounted volume contents, which have their own archives. Nonpersistent tmpfs contents are excluded and recorded as such. External databases, object stores, DNS, host services and containers you did not select need their own coordinated backup. There is no space or project filter for a full-instance capture.

Use a dedicated private vault outside every captured mount source, with room for both staging and the retained snapshot. The vault defaults to a 100 GiB application preflight limit and retains older generations; it does not prune them automatically. Snapshots contain credentials and must be protected as carefully as the running server's data directory. Copy the complete vault to independent storage for protection against disk loss.

Verification and recovery

verify checks the immutable manifest and every saved file's SHA-256. It leaves the backup unchanged and works without the primary hub. This proves the saved bytes match the manifest; test startup separately to confirm the recovered deployment works with its host and external services.

restore verifies and copies the complete prepared bundle into a new, previously nonexistent directory outside the vault. It never overwrites a running deployment, extracts volume archives, loads images or starts containers. Use deployment.json to identify each archive and reconstruct the deployment manually on the recovery host: load the exact images, restore the container filesystem changes and persistent mounts, recreate the recorded runtime configuration and networks, then start and validate the recovered stack before switching traffic.

File and directory modes are preserved where the host supports them. Mount archives retain the UID/GID, modes and links emitted by Docker; apply them with suitable tools when restoring the actual Linux volumes. UID/GID mappings, ACLs, extended attributes and security labels may need additional host restoration. Docker's archive format and the target filesystem determine which metadata can be recovered. The CLI preserves archive bytes without interpreting them, so recovery on Windows does not silently flatten the Linux mount metadata.

Recovery UI independent of the primary hub

The same built app can run against a local vault while the primary hub is offline, without a database connection or a primary-hub sign-in:

spacehub subhub serve --storage /srv/instance-vault --restore-root /srv/instance-restores --token-file /srv/recovery-token

Open the printed URL, normally http://127.0.0.1:4092/#/settings. --listen 127.0.0.1:4092 changes the loopback port; public listeners are not supported. --source <hub-name> labels the source. The service needs the built app assets (npm run build in app/ for a source checkout). It serves backup listing, verification and new-directory restore, with restores restricted to children of --restore-root. The default restore root is spacehub-restores alongside the vault. --token-file creates or reuses a private recovery key for a web-service connection; keep it secret. The local browser receives a separate recovery session cookie.

Recovery in the main web service

The web service exposes the same UI through the protected /-/api/instance-recovery endpoints. Configure a local vault with SPACEHUB_RECOVERY_DIR, an allowed restore parent with SPACEHUB_RESTORE_ROOT. SPACEHUB_PUBLIC_URL (or the database name) labels the source. Explicitly delegate access to registered builder usernames with comma-separated SPACEHUB_RECOVERY_OPERATORS; once any are named, only they qualify, and otherwise only the global administrator recorded by the module does. The app hides the Sub-hubs section and sub-hub pages from everyone else (/-/api/me reports operator), and the endpoints refuse them. The web service uses its private SPACEHUB_ADMIN_TOKEN to check that administrator identity. SPACEHUB_RECOVERY_STATE_DIR chooses the private connected-machine registry; otherwise it is stored under the server's persistent root or CLI home.

Alternatively, set SPACEHUB_RECOVERY_URL and SPACEHUB_RECOVERY_TOKEN to connect the main web service to a separate recovery service. The URL must use HTTPS or loopback HTTP and be reachable from the web process; the token is the private key from that service's --token-file. A remote HTTPS proxy must set the upstream Host to 127.0.0.1:4092 (or the configured loopback port) and omit the browser's Origin header on the bearer-authenticated upstream API request. The main web service still checks global operator access before forwarding the fixed recovery routes. It sends the recovery credential, without forwarding browser cookies or builder credentials. Choose either a local vault or this remote connection. Keep the standalone recovery UI available as well: the main hub's UI and sign-in depend on the primary database.

After changing the module, regenerate the client bindings with cd cli && npm run generate. cd cli && npm test then asks you to decide on the client protocol: if CLIs built before the change break (a table, column, reducer or procedure they use is renamed, removed or changes type, or a table gains a column), bump PROTOCOL and OLDEST_PROTOCOL in module/src/protocol.ts; either way, set BINDINGS_HASH there to the hash the test prints. Unit tests need no server: cd module && npm test runs the reducers in SpacetimeDB's in-process harness, and cd cli && npm test runs the xo API against a stand-in database, and autosync and the GitHub sync's rules against plain git repositories.

The app lives in app/: cd app && npm install && npm run build writes app/dist, which the web service serves at /-/app/ (in the image, SPACEHUB_APP_DIR=/opt/spacehub/app). Without the proxy, open the web service's own port (SPACEHUB_WEB_PORT, 3002) to use it; cd app && npm run typecheck checks it. Its look comes from open-chat, which ported it from CopilotKit/OpenMuse (MIT, notice in app/OPENMUSE-LICENSE).

How it works

Data model

Table Key Holds
user identity a builder's name
space name a top-level space: personal (a builder's), org or agent (with its parent space); display name, description, creator
space_role space + member a space's owners and members
project space/project a project: its space (owner), description, default branch, object counters, timestamps
project_import project GitHub source, import status
project_builder project the credited GitHub builder: login, display name, profile
activity id (time, project indexed) one row per change: who, what, which space or project and ref, commit, count, text
git_ref project + ref name refs/heads/* and refs/tags/*, mapped to object ids
git_object project + oid kind, size, raw body (inline up to 1 MiB) and pos, its place in the project's object log
object_chunk project + oid + index 1 MiB pieces of larger objects
project_member project + builder a project's collaborators
agent name an agent's identity and creator (its space is in space, kind agent)
agent_secret name (private) an agent's token, read only through agent_token by its owners
github_account GitHub account id (private) a builder who signed up with GitHub: its login then, its name, identity and token; written by github_link_builder (admin only), read by the web service to sign the account in again
hub_state key (private) the hub's settings: its admin, and where builders come from (accounts: open, github or xo)
space_link space the GitHub account it mirrors, the last sync's status and time
ref_sync project + ref GitHub's value at the last sync, and whether the hub's copy follows it or diverged
project_size project the bytes of its git objects, uncompressed, as git counts them; kept as objects arrive
presence connection which project (or whole space) a connected client follows, its mode and branch (or an agent's host), and its last heartbeat

Push. The helper lists the objects the project lacks (git rev-list --objects <new> --not <remote refs>). It uploads them in batches of about 4 MiB, and chunks objects over 1 MiB. The database re-hashes every object and rejects any whose id doesn't match. Then each ref moves through update_ref, which checks four things:

  • The caller owns or belongs to the project's space, or collaborates on the project.
  • The ref still holds the value the pusher listed (compare-and-swap).
  • Unless the push is forced, a branch move is a fast-forward. The database walks commit parents itself to check this.
  • An existing tag doesn't move unless the push is forced.

--force-with-lease is honoured.

Fetch. The helper subscribes to the project's objects in windows of about 8 MiB, ordered by pos, and writes the missing ones into the repo as a packfile. .git/spacehub/ records how far it has read, so later fetches only download newer objects. If that record is out of date, the helper re-reads the whole project.

Sync. Refs are rows, so project watch and project sync --watch hear about a push as soon as it commits. No polling is involved.

Presence. A long-running command calls watch_project with its project, mode and branch (or watch_space with a whole space), and repeats it every minute as a heartbeat. The row is keyed by the connection, so SpacetimeDB's client_disconnected removes it when the command stops. If a connection vanishes without closing, its row is swept by the next client_connected once its heartbeat is three minutes old, and pages and project who hide it as soon as it is stale.

Names. A space is a top-level name and a project is a repository, in the tables, columns, reducers and activity alike. Reducers that act on one project are named for it and take its full name as project (create_project takes the space and the name): delete_project, edit_project, set_project_builder, add_project_member, remove_project_member, watch_project, put_objects, update_ref, start_import, and so on. Reducers for a space take space: edit_space, watch_space, add_space_member, create_org, link_space. A CLI from before 0.4 cannot talk to this hub (its reducers are gone); update it.

Client protocol. On every connect the client calls the client_protocol procedure, which answers with the protocol the hub speaks and the oldest client protocol it still serves (module/src/protocol.ts). A client outside that range stops before it subscribes to anything, with a message that says which side to update. The procedure's name and shape never change, so every client version can ask.

xo

xo.quirq.dev checks who an xo user is with Clerk and keeps everything else here: each user's projects, spaces with their refs, and invites, as one JSON record per Clerk user in the private xo_record table. It also asks the hub for the user's builder, whose token the user's xo then pushes with. A builder is a GitHub account, so an xo user's builder is the builder of the GitHub account they connected to XO (Clerk keeps it; xo.quirq.dev sends its id and login): the same builder spacehub auth login and Sign in with GitHub reach, made on the first sign-in either way. The private xo_link table holds which GitHub account each xo user connected. Their xo username becomes the builder's display name and, when it is a free name here and no one else's GitHub login, a second name: space_alias, a public table, so /<xo username>/... shows the same pages as /<GitHub login>/... (the app moves the address to the GitHub login), and the CLI, git remotes and every reducer take either name; nobody else can take it. Without a connected GitHub account, xo.quirq.dev says where to connect one, and the website sends the visitor there. A builder xo made before GitHub was needed (named after the xo username, in the private xo_agent table) becomes the GitHub account's on its next sign-in: renamed to the GitHub login with its token, projects and places kept, or merged into the builder GitHub sign-in made (its projects move, a clashing name gets -<old name> after it), and its old name stays as a second name. These tables are written only through admin reducers (xo_put_record, compare-and-swap on the record's version, xo_link_github, and xo_link_agent for xo servers from before).

  • The admin is the identity that owns the database. The entrypoint calls claim_admin right after every publish; the first claim sticks, and if another identity ever holds it the server refuses to start.
  • GitHub sync runs as the admin too: the entrypoint always hands the admin's token to the web service, whose sync may create projects and push only in spaces linked to GitHub (shown as "GitHub sync" in the activity). git sees that token only when it pushes into the hub.
  • GitHub sign-up is the admin as well: the web service checks the GitHub token with GitHub, then makes the builder with github_link_builder (see cli/src/signin.ts). It is off only with SPACEHUB_ACCOUNTS=xo.
  • Turn it on by setting SPACEHUB_XO_KEY (32 characters or more, the same value as xo.quirq.dev's XO_HUB_KEY). The web service then answers /-/api/xo/v1/ (see cli/src/xo.ts) with that key only, acting as the admin over SpacetimeDB's HTTP API inside the container. People still sign up with GitHub (or as SPACEHUB_ACCOUNTS says); SPACEHUB_ACCOUNTS=xo leaves xo as the only source of builders. Names are shared: a second name is taken like any other.
  • Launching agents needs xo. On a hub with xo, members of an org with agents launch and steer them only once their account is linked to XO (signed in with xo); signed in with GitHub alone they chat and follow the workers, and the chat says to sign in with xo to launch.
  • Sign in with xo on the website (cli/src/xosignin.ts): the button takes the visitor through the same Clerk sign-in as xo login, and back signed in as their builder, made on the first sign-in. The hub is a client of xo login's Clerk OAuth application (public, with PKCE): GET /-/login/xo keeps a random state and a verifier for 10 minutes, ties them to the browser with an HttpOnly cookie, and sends it to Clerk; GET /-/login/xo/callback checks the state against that cookie (once only), then asks the xo server, with SPACEHUB_XO_KEY, to swap the code (POST <xo>/login/hub with the code, verifier and callback). The xo server answers the Clerk user and their builder, making it as xo login would; the hub reads the builder's token (from xo_link and github_account, or xo_agent for one made before) and puts it only in the usual session cookie. With no GitHub connected to XO, the xo server's 409 names where to connect one, and the page links there and back to Sign in with xo. No token or verifier is in a URL, the code works once and only with the verifier kept here, and nothing in the browser talks to the xo server. The button shows only while the xo server's GET /login offers this hub's own callback (as the browser reached it), which it does once the callback is a redirect URL of that OAuth application and XO_HUB_LOGIN_REDIRECT is set there; the answer is kept for 5 minutes. Without it, the terminal steps are all there is, as before.
  • Names. xo's record was designed when a hub space was one repository, so its "spaces" are hub projects today, and an xo project (a group of repositories) is closest to a hub space. The hub stores the record as opaque JSON, so nothing breaks; xo's own code should rename to match.

Workers on your own runners

Workers start from a project's chats and run on the launcher's own runner, on the launcher's own account. A runner is anything that speaks the Worker Protocol (worker/1, below); an Agents Hub is the first.

  • Connect a runner in Settings → Runners: enter its address and press Connect. space-hub sends you to the runner, you approve there, and it sends you back connected: the runner gives space-hub's server a token that only sees the workers space-hub starts (an OAuth-style code exchange with PKCE; the token is never in a URL or the browser). A runner without that button takes a pasted token instead: on an Agents Hub, Settings → Agent access, with "Only tasks it starts". Either way the token is sealed with SPACEHUB_SECRET_KEY and never goes back to a browser. Several runners are fine; one is the default. Disconnect revokes a token space-hub got through Connect; a pasted token is yours, so it is left alone.
  • Connect Agents Hub (with SPACEHUB_LAUNCHPAD_API): one button, one XO sign-in. space-hub sends you through XO's sign-in ("Allow access") and swaps the code itself for a short-lived pass, the way xo login does. With it, Launchpad lists your apps: your Agents Hub is found (even while it is still starting) and the usual Connect follows. Without one, Settings shows a dialog linking Launchpad's own create page (SPACEHUB_LAUNCHPAD_CREATE_PAGE), which fills the hub's XO API key, and watches for the new hub in the background: once it shows up, Connect follows by itself, with no second sign-in. The pass stays only in the server's memory: dropped as soon as your hub is found, when you close the dialog, or after 10 minutes at most; never stored, logged, sent to the browser, or put in a cookie or URL. Clerk's refresh token is never read.
  • Launch. In a channel, write what the worker should do and press the rocket beside Send. The tray picks the runner (when you have more than one) and, if the runner works on repositories, asks for owner/repo or an issue or pull request link. Only people who can write to the project launch there. A launch carries an idempotency key, so a retry never starts a worker twice.
  • Everyone in the space follows it. Under the message, members see the worker "on 's Agents Hub": what it is doing, its steps (when the runner shares them) and its result. Only the launcher stops it, follows up or tears it down, and only when the runner can.
  • The result is kept. When a worker ends, space-hub keeps a copy of its summary and links, so the card still shows them after it is torn down ("Torn down · result kept") or while its runner is disconnected. Connect the same runner again and its workers come back to it. Settings → Your workers lists everything you launched, with a nudge to tear down idle ones.
  • In the files. A launch is an ordinary chat turn by the launcher, ending with <!-- agenthub:task=<id> -->; the task's text says who launched it from which conversation.

The Worker Protocol a runner speaks, with Authorization: Bearer <token>: GET /api/worker ({protocol: "worker/1", name, kind, capabilities: {followUp, stop, events, repo, connect}}; without a token only protocol and capabilities), and tasks at POST /api/tasks, GET /api/tasks/<id>, /events?after=, POST /messages, POST /stop and DELETE. A runner with connect also serves /connect (the consent page, with client, redirect_uri, state and an S256 code_challenge), POST /api/connect/token {code, codeVerifier, redirectUri} and DELETE /api/tokens/self. The browser only talks to /-/api/runners and /-/api/workers (see cli/src/workers.ts); only the protocol's fields of a runner's answers reach it, and its token is taken out of a worker's steps.

Limits (v0)

  • Mirroring is GitHub to hub, public repositories only.
  • Every project can be read by anyone who can reach the server. Only its space's owners and members and its collaborators can push; they can do anything a push does, including force pushes and deleting branches. To be one builder on several machines, sign in with the same GitHub account, or use auth token and auth login --with-token.
  • Autosync commits often and with generated messages; squash before sharing the history elsewhere if that matters. It skips commit hooks.
  • Anyone with a GitHub account can sign up (with SPACEHUB_ACCOUNTS=open, anyone who can reach the server registers any free name; with SPACEHUB_ACCOUNTS=xo, only xo makes builders). Builders can create orgs and import public GitHub repositories (up to SPACEHUB_IMPORT_MAX_MB each). Keep that in mind before exposing a server publicly.
  • Org names are not checked against GitHub: an org can take a name that a GitHub user would later want, and that user then cannot sign up until the admin frees it.
  • GitHub sign-up sends the token gh holds (often with wide scopes) to the hub once. The hub uses it for one GET /user and drops it, but you are trusting the hub with it for that moment.
  • Objects are stored whole and uncompressed, in SpacetimeDB's memory. That suits code, not big binaries. The object size cap is 100 MiB.
  • Transfers carry whole objects, not deltas. There are no shallow clones. Only SHA-1 repositories are supported.
  • An interrupted push can leave unreferenced objects behind. They are harmless, and the retry skips them.
