xo is the command line for the XO Cloud core API. Every endpoint is a command, and xo sends your XO API key on each request without ever printing it.

It follows the shape of quirq's own tools (qq fetch, qqsync): one Python package, one argparse command, standard library only, Apache-2.0. Unlike them the command is plain xo.

Install

For a step-by-step setup on your own Mac or Linux machine, see docs/quickstart.md; for every command and how to test them, the user guide.

pip install "quirq-xo @ git+https://github.com/quirq-ai/xo"

Python 3.11 or newer. The package is quirq-xo, not xo: PyPI's xo is an unrelated game, and pip install -U xo would replace this tool with it. The command it installs is xo.

A GitHub project is called by its repo's name in every command (project:headscale); when another of your projects has that name, call it by its OWNER/REPO (its folder is then ./OWNER/REPO). A repo named like such an OWNER folder goes in ./OWNER/REPO too (suraj/suraj beside suraj/react), so no project's folder is ever inside another's. A checkout an older xo put in ./OWNER/REPO is still used there.

xo projects, xo list projects, xo create project and xo connect P --repo print your projects as [{"name": "headscale", "owner": "juanfont"}, {"name": "notes"}]; a plain project has no owner. Your metadata still records a GitHub project as juanfont/headscale, so nothing stored changes.

Every space on XO is created with xo create space NAME KIND; the old xo claude-code, xo codex, ... commands are gone and say so. It prints the recorded space and XO's answer, id included, and xo spaces (or xo list spaces) shows it again later. The API has no list, delete, start or stop endpoint, so xo spaces --space-id ID is the only way to XO's own view of a space.

The API is XO's platform, https://dev.xo.builders/api/core/v1 (the xo service); xo reaches it through the xo server (see Server mode and Services). Its spec is bundled with xo as src/xo/openapi.json, written from the xo-swarm source (app/api/[[...slugs]]/route.ts and types/*-schema.ts at 6dddd07aa) because the interactive docs sit behind a browser sign-in. To use another spec, pass --spec FILE or set XO_SPEC=FILE.

Things to know:

  • A new space's NAME is 1 to 32 letters, digits or hyphens, starting with a letter or digit, and not new or create. It is the space's name on XO and in your spaces, in lowercase as XO keeps it (xo says so when it changes it). A name you already use fails.
  • --volume-size is in GB, 20 to 100.
  • A provider or channel flag sends that object with "enabled": true, so --providers-openai-api-key K sends {"openai": {"enabled": true, "apiKey": "K"}}.
  • The API checks the body before the key, so a bad body answers 422 with every problem listed, even with no key.
  • Every create except nebius-openclaw stores the XO API key you call with inside the new space, as its xo_api_key. That key can create spaces and read the connection URLs, session tokens included, of every space you own, so anything that can read the new space's environment (an agent steered by a message, say) can act as you. xo prints a line saying so before each such create, and cannot turn it off. If XO will issue you a second key, use that one for creates.
  • xo spaces --space-id ID prints spaceApiUrl and openClawRestartUrl, which carry a session token that expires within the hour. Treat them as secrets.
  • Provider keys and bot tokens given as flags land in your shell history, and even from a variable ("$ANTHROPIC_API_KEY") they show in the process list for as long as the request runs. Give the body with --data @body.json instead, or one key or token as - to type it (or pipe one line).
  • A body field the command does not know is refused, since the server would drop it and create the space without that setting; xo api sends any body as given.
  • If a create times out or is interrupted, the server may still have made the space: check before you retry.

Services

One xo login covers two services, plus GitHub through the GitHub CLI (gh). The xo server lists the two at /config (no key needed); xo ships the same list (src/xo/services.json) and uses its own copy when the server cannot give a good one. The names follow the commands: xo for the creates, and me for the xo server that answers xo me:

{
  "schema": "xo-services/2",
  "xo": { "url": "https://dev.xo.builders", "about": "..." },
  "me": { "url": "https://xo.quirq.dev", "about": "..." }
}
Service Address How you log in Commands
me the xo server: --url, XO_URL, the one xo login saved, else https://xo.quirq.dev (the me address in xo's own list) your XO API key xo me
xo https://dev.xo.builders, reached through the xo server the same XO API key xo create space NAME KIND and xo spaces --space-id ID
github https://github.com (not in the list; always github.com) the GitHub CLI's own login (gh auth login), in your browser gh, and git over https if you let gh set it up

Every XO API command, creates included, goes to the xo server you logged in to: xo sends your key to that one address, and the server passes it on to the xo address with each create. xo does not use a served list's me address; the key's address is always --url, XO_URL, the one xo login saved, else https://xo.quirq.dev.

Changed: XO's platform is now https://dev.xo.builders, not https://app.xo.builders. Every create carries your XO API key, and it now goes to dev.xo.builders. The xo server takes the new address on its next deploy unless XO_CORE_API_URL is set in its environment (in Vercel), which overrides it; set XO_CORE_API_URL=https://app.xo.builders/api/core/v1 to keep the old one.

The list holds addresses only, never keys. Keys stay on your machine: the XO key in ~/.config/xo/credentials, gh's token wherever gh keeps it. xo checks a served list: no key is sent for it, no redirect is followed, every address must be plain https, and unknown services are skipped with a line. xo login xo (or me) or xo login github does one service; xo-server and xo-platform, the names before xo-services/2, still work. xo logout deletes the key and asks before logging gh out of github.com.

Server mode

XO API commands go to one address, the xo server (https://xo.quirq.dev, or XO_URL, or the one xo login --url saved). xo me reads your Clerk account, which needs Clerk's Secret Key. That key never goes on a user's machine: the same package runs as a server, xo serve, on one deployment that holds it. The server passes every other command (the creates and xo spaces --space-id ID) on to XO's core API under its /api/core/v1, with your key, as sent. XO's platform checks keys with the same Clerk instance as that deployment, so a key from another instance gets 401 from both. See docs/server.md and, to deploy it, docs/deploy-vercel.md.

How commands are named

The command is the path without a leading /api or /vN and without its {placeholders}, joined with dashes. When several methods share a path, each is an action: list and get (GET on the collection or one item), create (POST), update (PATCH), replace (PUT), delete (DELETE). Path, query and header parameters and the fields of a JSON body are the flags; a field nested in an object is named by its path (providers.anthropic.apiKey is --providers-anthropic-api-key). A body field the spec types as a string keeps the text you type; other values are JSON when they parse. Required ones are checked before anything is sent. A spec that cannot be read leaves ops, call and api working and makes generated endpoint commands stop with one line saying why. The built-in login, logout and serve commands also work independently of the spec.

Lower level

xo ops                          # every operation: id, method, path, summary
xo ops openclaw                 # only those whose id, path or tag mentions "openclaw"
xo ops spaces --json            # the same with their parameters
xo call create_codex --data '{"name": "my-codex", "volumeSize": 20}'
xo call create_codex --field name=my-codex --field volumeSize=20   # the body field by field
xo call create_openclaw --data @body.json                           # or from a file, or - for stdin
xo call get_space --param spaceId=ID
xo call create_codex --field name=x --field volumeSize=20 --dry-run # print the request, send nothing
xo api GET /spaces/ID                                               # any request, spec or not

Through the xo server only the creates and GET /spaces/{spaceId} pass; any other xo api request, or an extra operation from your own --spec, gets the server's HTTP 404: Not found. To send one straight to XO, add --url https://dev.xo.builders and give the key with XO_API_KEY or --api-key - (the key xo login saved is only sent to the address it was saved with, so a one-run --url always needs one of those).

--param fills path, query and header parameters, never Authorization, Host, Cookie, Proxy-* or the other headers xo and HTTP own. --field values are JSON when they parse (false, 5, ["a"]) and plain strings otherwise. A request that is not a GET changes things on XO, so it prints one line on stderr before it goes. --dry-run needs no key and sends nothing. It prints the request with the provider keys and bot tokens the spec marks as secrets shown as <hidden>; add --show-secrets to see them. Those keys and tokens are redacted from responses and errors too, like the API key. Responses print as JSON on stdout. Any problem exits 1 with one line on stderr.

--api-key KEY also works, but the key then lands in your shell history and in the process list other users of the machine can read. Prefer xo login, the variable, or --api-key -. The flag wins over the variable, and the variable over the saved key. The saved key is only sent to the address it was saved with. xo refuses a saved key file that other users could read, or that is a symlink. The options go before or after the command.

Safety

  • The key goes only in the Authorization: Bearer header. xo reads the spec only from a file (the bundled one, --spec or XO_SPEC); it never fetches one from the API with your key. It is redacted from any response or error that echoes it, and tests check it never reaches stdout or stderr, including on argument errors and unexpected failures. An argument error never repeats a value you typed, so a mistyped key flag (--api_key KEY, --token=KEY, --api-keyKEY) stays off the screen. A key with anything but letters, digits and _ . - + / = is refused without being shown, and the key is also redacted where escaping changes any of its characters, in any mix: URL escaping (%2F, in either case, or double-encoded as %252F, and + read as a space), JSON (\/, \u002f) and HTML (&#x2F;, &#47;, zero-padded or not, and &sol;).
  • xo never follows a redirect, so a redirect cannot carry the key to another host. A redirect to XO's sign-in page is reported as "this route does not accept an API key".
  • Plain http:// is refused except to this machine.
